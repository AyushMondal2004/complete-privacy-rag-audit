# Privacy-RAG-Audit

A **Retrieval-Augmented Generation (RAG) pipeline for auditing mobile app
privacy policies**, evaluated against the **APP-350** human-annotated
benchmark corpus. The project compares chunking strategies (fixed-window
vs semantic) and retrieval thresholds to measure how accurately a local
LLM (via Ollama) can extract privacy data-collection practices from raw
policy text — scored automatically with Precision/Recall/F1 against ground
truth, and reviewable through a small web frontend.

> **Disclaimer:** This tool provides RAG-based decision support. It is
> **not legal advice**. Findings are generated by a language model reading
> retrieved policy excerpts and may be incomplete or incorrect — always
> verify against the source policy.

---

## What this project does

1. **Ingests** the APP-350 corpus (350 real mobile-app privacy policies as
   HTML, each with human-annotated ground-truth labels of what data
   practices the policy actually describes).
2. **Chunks** each policy's cleaned text three different ways:
   - `fixed_300` — 300-word sliding windows, 50-word overlap
   - `fixed_500` — 500-word sliding windows, 75-word overlap
   - `semantic` — sentence-embedding similarity breakpoints
3. **Embeds and indexes** chunks per-config into ChromaDB (cosine
   similarity).
4. **Retrieves** evidence per policy using six targeted category queries
   (contact info, location, identifiers, demographics, third-party
   sharing, SSO), merged and de-duplicated.
5. **Generates** structured predictions with a local LLM (`qwen2.5:7b` via
   Ollama), constrained to the exact APP-350 label vocabulary and a strict
   JSON schema.
6. **Evaluates** predictions against ground truth (label normalization →
   TP/FP/FN → Precision/Recall/F1), per-policy and aggregated.
7. **Analyzes** results: config comparison, per-policy variance, error
   category breakdown, retrieval-threshold sensitivity sweep, and a
   manual/qualitative review sampler.
8. **Visualizes** everything as charts, and serves a live demo through a
   FastAPI backend + a static HTML frontend (audit an indexed APP-350
   policy, or upload your own).

# privacy-rag-audit — Full Code & File Explanation

This document walks through every file you shared, what it does, how it connects
to the rest of the pipeline, and the step-by-step process the system follows
end-to-end.

---

## 0. Big picture

This is a **RAG (Retrieval-Augmented Generation) pipeline that audits mobile
app privacy policies**. Given a policy's HTML text, it:

1. Cleans and chunks the text (three competing strategies are compared).
2. Embeds chunks into a vector store (ChromaDB).
3. At query time, retrieves the chunks most relevant to a fixed set of
   privacy-practice questions (location, contacts, identifiers, etc.).
4. Sends those retrieved excerpts to a local LLM (via Ollama) with a strict
   prompt that forces it to classify practices using the **APP-350
   annotation vocabulary**.
5. Compares the LLM's predicted practices against APP-350's human-annotated
   ground truth, computing Precision/Recall/F1.
6. Repeats this across three chunking configs and a threshold sweep to find
   which retrieval configuration audits privacy policies most accurately.
7. Surfaces results through CSVs, charts, an error-analysis report, and a
   small web frontend backed by a FastAPI service.

This is effectively an **evaluation harness for a RAG design-choice
question**: "does chunking strategy (fixed-window vs semantic) and
similarity threshold change how well an LLM extracts privacy practices from
policy text, when scored against a trusted human-annotated benchmark
(APP-350)?" That framing is exactly what you'd want for an MSc-style
dissertation on RAG pipeline evaluation.

## 1. Dataset — `APP-350_v1_1.zip` / `data/raw/APP-350_v1.1/`

Confirmed from the zip listing:
- `original_documents/*.html` — one HTML file per app, named by `policy_id`
  (e.g. `340.html`, `205.html`). This is the raw source text the pipeline
  cleans and chunks.
- `annotations/policy_*.yml` — ground truth: for each policy, a list of text
  segments each carrying one or more `practice` + `modality`
  (`PERFORMED`/`NOT_PERFORMED`) annotations. This is what `loader.py` reads
  via `load_ground_truth`.
- `documentation/` — dataset README, annotator instructions, and
  inter-annotator agreement stats (useful methodology citations for a
  dissertation, not used programmatically).
- `LICENSE` — dataset license.

This is the OPP-115-style **APP-350 corpus** — a known benchmark for mobile
privacy-policy practice annotation, which is why `label_matcher.py`'s
vocabulary (`Contact_E_Mail_Address`, `Location_GPS`, `Identifier_Ad_ID`,
etc., each suffixed `_1stParty`/`_3rdParty`) mirrors its schema exactly.

## 2. Configuration files

### `.env`
Runtime settings read via `python-dotenv` / `os.getenv`:
- `LLM_BASE_URL` / `LLM_MODEL` — points `llm_client.py` at a local Ollama
  server running `qwen2.5:7b`.
- `EMBEDDING_MODEL` — `all-MiniLM-L6-v2`, used by `embedder.py`.
- `CHROMA_PERSIST_DIR` — where the vector DB is written to disk.

### `experiments/configs/{fixed_300,fixed_500,semantic}.yaml`
Each YAML is a **chunking + retrieval configuration** consumed by
`scripts/01_build_vector_db.py` and `scripts/02_run_experiment.py`:
- `fixed_300` / `fixed_500`: sliding-window word chunking with different
  window sizes and overlaps.
- `semantic`: sentence-embedding breakpoint chunking with a similarity
  threshold and min/max chunk word bounds.
- All three share `top_k` (chunks per query) and `similarity_threshold`
  (retrieval cutoff) so the *comparison* is fair — only chunking strategy
  varies, retrieval params held constant (except in the dedicated
  `threshold_sweep`).

### `requirements.txt`
Standard stack: FastAPI + uvicorn (API), ChromaDB (vector store),
sentence-transformers (embeddings), BeautifulSoup+lxml (HTML cleaning),
PyYAML (config + ground truth), pandas/numpy (data wrangling/metrics),
requests (calling Ollama's HTTP API), tqdm (progress bars).

### `.gitignore`
Keeps the repo lean — excludes the virtualenv, `__pycache__`, and both
`data/raw/` and `data/processed/` (the corpus and vector DB are
regenerated/downloaded locally, never committed).

## 3. Ingestion — `src/ingestion/`

### `loader.py`
- `RawPolicy` dataclass: `policy_id` + path to its HTML file.
- `iter_raw_policies(raw_dir)`: globs `**/original_documents/*.html`,
  yields a `RawPolicy` per file, using the filename stem as `policy_id`.
- `load_ground_truth(policy_id, raw_dir)`: globs
  `**/annotations/policy_{id}.yml` and parses it with `yaml.safe_load`.
  Returns `None` if no annotation exists (that policy is unlabeled and
  excluded from scored experiments, but can still be chunked/indexed).
- `count_available_policies`: simple count helper.

This is the **single source of truth** for "which policies exist" and
"what's the correct answer for policy X" — every script that touches raw
data imports from here.

### `html_cleaner.py`
- Uses BeautifulSoup (`lxml` parser) to strip `script/style/nav/noscript/
  svg/iframe` tags (noise removal).
- Converts heading tags (`h1`–`h4`) into `\n\n## {heading text}\n` markers
  **before** extracting text — this is important: it's what lets
  `structural_chunker.py` later split on `## ` regex markers, and gives the
  semantic/fixed chunkers cleaner sentence boundaries.
- `_normalise_whitespace`: collapses repeated spaces/blank lines, strips
  each line.
- Returns a `CleanedPolicy` dataclass (`text`, `n_headings`, `n_chars`) —
  used both for chunking and for lightweight corpus stats.

---

## 4. Chunking — `src/chunking/`

All three strategies produce the same output type:

### `base.py`
`Chunk` dataclass: `chunk_id`, `policy_id`, `text`, `position`,
`config_name`, optional `section_heading`, and a free-form `metadata` dict.
This uniform shape is what lets `chroma_store.add_chunks` treat all
strategies identically.

### `fixed_chunker.py`
Classic **sliding window over words**: splits `text.split()`, then walks in
steps of `chunk_size_words - overlap_words`, slicing `chunk_size_words`-word
windows. Stops once the last window reaches the end of the text (so no
duplicate trailing chunk). Straightforward, strategy-agnostic to sentence
or section boundaries — chunks may cut mid-sentence.

### `structural_chunker.py`
Splits on the `## heading` markers inserted by `html_cleaner.py`
(`HEADING_PATTERN`). Each section becomes a chunk (further split by
`MAX_SECTION_WORDS=400` if too long). Preserves `section_heading` metadata.
Note: this strategy is defined but **not** one of the three configs
actually compared in the experiments (`fixed_300`, `fixed_500`,
`semantic`) — it's available as a fourth option via
`build_chunks`'s `elif cfg["strategy"] == "structural"` branch in
`01_build_vector_db.py`, but no `structural.yaml` config was shown, so it's
effectively a latent/unused strategy in the current experiment set.

### `semantic_chunker.py`
The most sophisticated of the three:
1. Splits text into sentences via regex on `.!?` boundaries.
2. Embeds every sentence with the passed-in `embed_fn` (wraps
   `embedder.embed_texts`), then L2-normalizes each embedding vector.
3. Walks sentence-by-sentence, computing cosine similarity between
   consecutive sentence embeddings (`sim = dot(emb[i-1], emb[i])` — valid
   as cosine similarity because vectors are pre-normalized).
4. A new chunk boundary is triggered when either:
   - `sim < similarity_threshold` **and** the current chunk already has
     ≥ `min_chunk_words` (avoids tiny chunks from a single low-similarity
     jump), or
   - Adding the next sentence would exceed `max_chunk_words` (hard cap).
5. Produces variable-length chunks that (in theory) group topically
   coherent sentences together — the hypothesis being this should retrieve
   more precise, less noisy evidence than fixed windows.

## 5. Embeddings — `src/embeddings/embedder.py`
- Wraps `sentence_transformers.SentenceTransformer`, defaulting to
  `all-MiniLM-L6-v2` (fast, 384-dim, good for this scale of local
  experimentation).
- `@lru_cache(maxsize=1)` on `_get_model` avoids reloading the model
  weights on every call — it's loaded once per process.
- `embed_texts(texts)` batches encoding (`batch_size=32`) and returns a
  numpy array. Used by: chunking (semantic breakpoints), indexing
  (chunk embeddings for Chroma), and retrieval (query embeddings).

---

## 6. Vector store — `src/vectorstore/chroma_store.py`
- `get_client()`: lazy singleton `chromadb.PersistentClient` pointed at
  `CHROMA_PERSIST_DIR`.
- `get_or_create_collection(config_name)`: **one Chroma collection per
  chunking config** (`fixed_300`, `fixed_500`, `semantic`), using cosine
  distance (`hnsw:space: cosine`) — this is the key mechanism that keeps
  the three strategies' indexes fully separate so they can be compared
  independently.
- `add_chunks(collection, chunks, embeddings)`: bulk-inserts, building a
  metadata dict per chunk (`policy_id`, `position`, `config_name`, optional
  `section_heading`, plus any scalar entries from `chunk.metadata`). Only
  `str/int/float/bool` metadata values are kept (Chroma's metadata
  constraint). Batches inserts at 5000 to stay within Chroma limits.
- `query_policy(collection, query_embedding, policy_id, top_k,
  similarity_threshold)`: queries Chroma **filtered to a single
  `policy_id`** (via `where={"policy_id": ...}`) — this is essential: each
  audit is scoped to one policy's own chunks, never cross-policy leakage.
  Converts Chroma's cosine *distance* to *similarity* (`sim = 1 - dist`),
  optionally drops results below `similarity_threshold`.

---

## 7. Retrieval — `src/retrieval/retriever.py`
- `CATEGORY_QUERIES`: six hand-written natural-language questions covering
  the practice categories (contact info, location, identifiers,
  demographics, third-party sharing, SSO/login).
- `retrieve_evidence(collection, policy_id, top_k, similarity_threshold,
  queries)`:
  1. Embeds all category queries at once.
  2. Runs each query embedding against `query_policy` (per-query top_k).
  3. **Merges and de-duplicates by `chunk_id`**, keeping the max similarity
     seen for any chunk retrieved by multiple queries.
  4. Returns chunks sorted by similarity descending.

  The code comment explains the design rationale directly: a single broad
  query with high top_k under-retrieves (only 8 results seen for policy
  108 in practice), whereas 6 targeted category queries at top_k=6 each can
  surface up to 36 distinct, more targeted chunks — deliberately trading
  more LLM context for better recall across all practice categories.

This module is the connective tissue between the vector store and
generation — it's called both by the main experiment scripts and directly
by the FastAPI `/experiment` and `/audit` endpoints.

---

## 8. Generation — `src/generation/`

### `prompts.py`
- `SYSTEM_PROMPT`: a long, carefully engineered instruction that:
  - Forces the model to process excerpts **in order**, one at a time, so it
    doesn't stop early after finding a few practices (a common LLM failure
    mode in multi-label extraction).
  - Explicitly warns against treating similar permissions (e.g. Bluetooth
    vs precise location) as duplicates.
  - Restricts output to an **exact closed vocabulary** matching APP-350's
    label scheme (`Contact_E_Mail_Address`, `Location_GPS`,
    `Identifier_Ad_ID`, `SSO`, `Facebook_SSO`, etc.), each suffixed
    `_1stParty` or `_3rdParty`.
  - Gives a precise rule for 1st vs 3rd party attribution: attribute by
    *who is performing the collection/use*, not who benefits or is merely
    named — with a worked example.
  - Demands strict JSON-only output matching a schema: a `practices` array
    of `{practice, modality, evidence, explanation}` plus a top-level
    `insufficient_evidence` boolean.
- `build_user_prompt(policy_id, evidence_chunks)`: formats retrieved
  chunks as a numbered list `[1] (similarity=0.83) <text>` — the numbering
  matches what the system prompt tells the model to iterate over.

### `llm_client.py`
- `call_llm(system_prompt, user_prompt, temperature=0.0)`: POSTs to a local
  **Ollama** server's `/api/chat` endpoint (non-streaming), deterministic
  (`temperature=0`) for reproducible eval runs. 420s timeout (7-b model on
  CPU/local GPU can be slow for long prompts).
- `parse_llm_json(raw_text)`: defensive JSON extraction —
  1. Strips Markdown code fences if present.
  2. Finds the outermost `{...}` span.
  3. Tries `json.loads`; on failure, calls `_repair_inner_quotes`.
- `_repair_inner_quotes`: a small state machine that walks the JSON string
  character by character, tracking whether it's "inside a string." If it
  hits a `"` that *doesn't* look like a real string terminator (i.e. the
  next non-whitespace char isn't `,`, `:`, `}`, or `]`), it assumes it's an
  unescaped quote **inside** a string value (common when the LLM quotes
  policy text verbatim in the `evidence` field) and escapes it. This is a
  pragmatic fix for a very common small-LLM JSON malformation.

## 9. Evaluation — `src/evaluation/`

### `label_matcher.py`
- `normalise_label(label)`: lowercases, converts spaces/hyphens to
  underscores, collapses repeated underscores, then applies
  `LABEL_ALIASES` — a small synonym map (e.g. `identifier_advertising` →
  `identifier_ad_id`, `contact_email` → `contact_e_mail_address`) so minor
  LLM phrasing drift doesn't count as a false positive/negative. Party
  suffix (`_1stparty`/`_3rdparty`) is preserved through alias resolution.
- `extract_ground_truth_labels(yaml)`: walks `segments → annotations`,
  keeps only `modality == "PERFORMED"` practices, normalizes them into a
  set.
- `extract_predicted_labels(llm_json)`: same idea, but reading from the
  LLM's `practices` array.
- `match_labels(policy_id, predicted, ground_truth)`: pure set arithmetic —
  `TP = predicted ∩ gt`, `FP = predicted - gt`, `FN = gt - predicted`.
  Returns a `MatchResult`.

### `metrics.py`
- `compute_metrics(tp, fp, fn)`: standard precision/recall/F1 with
  divide-by-zero guards.
- `aggregate(results)`: **micro-averaged** metrics — sums TP/FP/FN across
  all policies before computing P/R/F1 (as opposed to macro-averaging each
  policy's F1 then meaning them). This is the number reported as
  `*_summary.csv`.
- `per_policy_metrics(results)`: same computation but per policy, feeding
  `*_per_policy.csv` (used later for the boxplot and worst/best-policy
  tables).

## 10. API — `src/api/main.py`
FastAPI app with CORS wide open (`allow_origins=["*"]`, fine for local
dev, **not** for production).

- `GET /health`: liveness check.
- `POST /experiment/{policy_id}` (body: `AuditRequest{config_name, top_k,
  similarity_threshold}`):
  1. Opens the Chroma collection for the requested config.
  2. Retrieves evidence via `retrieve_evidence`.
  3. 404s if nothing indexed for that policy/config (tells the user to run
     `01_build_vector_db.py` first).
  4. Builds the prompt, calls the LLM, parses JSON.
  5. If ground truth exists for that policy, computes and returns metrics
     inline (same TP/FP/FN/P/R/F1 shape as the offline scripts) — this is
     what lets the frontend show live precision/recall/F1 for indexed
     APP-350 policies.
  6. Returns `AuditResponse{policy_id, predicted, evidence_used, metrics}`.
- `POST /audit` (multipart file upload, arbitrary policy HTML):
  1. Reads and decodes the uploaded file.
  2. Cleans it with `clean_html`, chunks with `chunk_fixed` (hardcoded
     300/50 — the "ad hoc" default, not configurable from the frontend).
  3. Embeds and indexes into a **throwaway** Chroma collection
     `ad_hoc_uploads`.
  4. Retrieves + generates exactly as above, but with **no ground truth**
     (arbitrary user-uploaded policy, unscored).
  5. **Deletes the ad_hoc_uploads collection** after use — so uploads don't
     accumulate in the persistent vector store; each upload audit is
     stateless.

## 11. Scripts — `scripts/`

### `01_build_vector_db.py`
The **indexing** entry point. For a given `--config` YAML:
1. Opens/creates that config's Chroma collection.
2. Iterates all raw policies (optionally capped with `--limit` for a quick
   pilot before indexing the full 350).
3. For each: read HTML → clean → chunk (dispatch on `cfg["strategy"]` to
   fixed/structural/semantic chunker) → embed all chunk texts → 
   `add_chunks` into Chroma.
4. Catches and logs per-policy exceptions without halting the whole run
   (`n_skipped` counter), prints a final summary.

Run once per config before any experiment/API use against that config.

### `02_run_experiment.py`
The **evaluation** entry point for one config, run against all **annotated**
policies (unlabeled ones are skipped since there's nothing to score
against):
1. For each policy with ground truth: retrieve evidence → build prompt →
   call LLM → parse → match labels → collect `MatchResult`.
2. `time.sleep(0.1)` between calls — a small throttle for the local LLM
   server.
3. Writes `results/{config}_per_policy.csv`, `_errors.csv` (if any), and
   `_summary.csv` (aggregate P/R/F1 + counts). This is the file that
   `03_compare_configs.py` later stitches together across all three
   configs.

### `03_compare_configs.py`
Trivial but important: globs all `results/*_summary.csv`, concatenates,
sorts by F1 descending, writes `results/comparison_summary.csv` and prints
it. This produces the "which chunking strategy wins" table — and is the
data source for `chart_config_comparison` in the visualisation notebook.

### `04_error_analysis.py`
Deeper diagnostic pass beyond raw P/R/F1:
1. Loads each config's `_per_policy.csv` and `_errors.csv`.
2. `categorise_errors`: classifies every policy into one of:
   `no_predictions_no_gt`, `missed_risk_only` (only FN), 
   `irrelevant_retrieval_only` (only FP), `mixed_errors` (both),
   `perfect_match` (TP>0, no FP/FN), `other`; plus, from the error log,
   `no_evidence_retrieved`, `formatting_failure`, `llm_timeout`.
3. Writes `results/error_analysis.csv` (row-per-policy category labels —
   feeds `chart_error_breakdown`'s stacked bar chart).
4. `generate_summary_md`: auto-writes `results/error_analysis_summary.md`
   with, per config: an error-category count table, a missed-vs-irrelevant
   breakdown (what % of *all* errors were false negatives vs false
   positives — telling you whether the system under- or over-predicts),
   and top-5 best/worst policies by F1 (for qualitative deep-dives in the
   dissertation write-up).

### `05_qualitative_sample.py`
Human-in-the-loop QA tool: randomly samples `--n` policies (seeded for
reproducibility), runs retrieval+LLM (no ground-truth scoring — this is
about **subjective quality**, not label accuracy), and writes:
- `{config}_sample_raw.json`: full raw predictions.
- `{config}_review_sheet.csv`: one row per predicted practice, with blank
  columns (`grounded_in_evidence`, `understandable`, `not_misleading`,
  `reviewer_notes`) meant to be filled in by hand — this is the
  **manual/human evaluation** complement to the automatic F1 metric
  (checking things F1 can't capture, like whether the "evidence" quote is
  real or hallucinated, or whether the explanation is misleading).

### `debug_one.py`
Single-policy trace tool for development: runs `fixed_300` retrieval +
generation for one `policy_id` (CLI arg, default `"108"`), prints raw
retrieved chunks with similarity scores, the raw LLM text output, the
parsed/normalized predicted vs ground-truth label sets, and the
matched/unmatched breakdown. This is the fastest way to debug a specific
failure without running the full experiment sweep.

### `inspect_chunks.py`
Even more minimal debug tool: opens the `fixed_300` collection, prints
total chunk count across all policies, then for one `policy_id` lists every
stored chunk's id, word count, and text preview. Useful for sanity-checking
that indexing actually happened and chunk boundaries look reasonable.

## 12. Threshold sweep — `experiments/threshold_sweep/run_sweep.py`
A more rigorous, **controlled experiment** than the main scripts: it holds
chunking config fixed and varies `similarity_threshold` (default sweep
`[0.0, 0.1, 0.2, 0.3, 0.4]`) across all three configs, to see how
aggressive/loose retrieval filtering affects P/R/F1.

Key design points:
- `sample_policy_ids`: takes a **fixed random subsample** (`DEFAULT_N=15`,
  `RANDOM_SEED=42`) of annotated policies rather than the full 350 — this
  keeps the sweep (configs × thresholds × policies × LLM calls) tractable,
  and caches the sampled IDs to `sampled_policy_ids.txt` so re-runs use the
  same policies unless `--resample` is passed.
- `run_one_threshold`: same retrieve→prompt→LLM→match loop as
  `02_run_experiment.py`, but parameterized by threshold, with per-run
  error logging.
- Results are cached to disk per config/threshold
  (`results/{config}/threshold_X_X.csv`); reruns skip existing files unless
  `--force`, and existing summary CSVs are also read back in to compose the
  final combined table — this makes the sweep resumable/incremental, which
  matters a lot given how slow local LLM calls are (the script even prints
  an estimated total runtime).
- `make_summary`: aggregates the sweep's per-policy rows into one row per
  threshold (micro-averaged P/R/F1), written to
  `results/{config}/summary.csv`.
- `main`: iterates configs × thresholds, writes
  `results/all_configs_summary.csv` at the end — the exact file consumed
  by `chart_threshold_sensitivity` in the visualisation notebook.

## 14. Frontend — `frontend/index.html`
A single self-contained HTML/CSS/JS page (dark theme matching the chart
styling), talking directly to the FastAPI backend at
`http://localhost:8000`. Two tabs:

1. **"Indexed Policy (APP-350)"**: enter a `policyId` + pick a chunking
   config → `POST /experiment/{policyId}` → renders:
   - Precision/Recall/F1 metric cards.
   - A label-comparison list (✓ matched / ✗ false positive / · missed),
     from the `metrics` object.
   - A **risk assessment** section: each predicted practice rendered as a
     card, tagged 1st/3rd party (`partyOf`, string-matched from the label),
     and assigned a **severity** (`SEVERITY_MAP` — location/device
     identifiers = high, contact/cookies/third-party = medium, SSO/1st-
     party generic = low) with a colour-coded badge and a risk-count
     summary panel (high/medium/low counts) — this is a UI-layer
     interpretive add-on; severity classification isn't part of APP-350's
     ground truth or the LLM's output, it's computed client-side purely
     for presentation.
2. **"Upload Policy"**: drag-and-drop or click to select a `.html` file →
   `POST /audit` (multipart) → renders findings only (no metrics, since
   uploaded policies have no ground truth).

Both flows share `renderFindings`/`escapeHtml` (XSS-safe text insertion)
and `setStatus` for inline status/error messaging. The footer includes an
explicit disclaimer that findings are LLM-generated, may be wrong, and
should be verified against source text — appropriate given this is a
decision-support/audit tool, not a legal conclusion.

## Method summary

- **Corpus:** APP-350 (350 annotated mobile app privacy policies).
- **Independent variables:** chunking strategy (`fixed_300`, `fixed_500`,
  `semantic`) and retrieval similarity threshold (swept `0.0`–`0.4`).
- **Retrieval:** 6 fixed category queries per policy, merged/de-duplicated
  by chunk, per-policy scoped (never cross-policy).
- **Generation:** single LLM call per policy per config, closed-vocabulary
  JSON extraction schema mirroring APP-350's `Practice_Party` label scheme.
- **Scoring:** label normalization (alias table) → set-based TP/FP/FN →
  micro-averaged Precision/Recall/F1, both per-policy and aggregate.
- **Qualitative validation:** separate manual review sampler, independent
  of the automatic metric, to catch issues F1 can't (hallucinated
  evidence, misleading explanations).
- **Error taxonomy:** every policy classified into a single error category
  (perfect match, missed-only, irrelevant-only, mixed, or pipeline
  failures like no-evidence/formatting/timeout) for structured discussion
  of failure modes.
